# Как сделать такую игру с нуля: промт и план

Документ для **нового, отдельного проекта** — не для `/Users/valera/Projects/Game`.
Здесь два раздела: стартовый промт, который отдаётся Claude Code в пустой папке,
и план из десяти фаз, переписанный «от нуля» (в текущем проекте порядок другой:
там сначала был прототип на клавиатуре, а фазы разбирали его под мобилки).

Опыт, вшитый в этот план, взят из Wormfall: 10 500 строк C#, ноль бинарных
ассетов, четыре платформы. Всё, что там стоило отдельной сессии отладки,
здесь вынесено в предусловия фаз.

---

## 1. Стартовый промт

Кладётся в пустую папку как первое сообщение. Он не просит писать код сразу —
он задаёт рамку, в которой все последующие «Фаза N» работают одинаково.

```
Делаем 2D-артиллерию в духе Worms на Unity 6. Проект новый, папка пустая.

Продукт: пошаговый бой команд червей на разрушаемом ландшафте. Ветер,
баллистика, урон по радиусу, откидывание взрывом, падение в воду. Матч —
на четырёх платформах: iPhone, Android, Mac, Windows.

Жёсткие правила проекта, соблюдать без напоминаний:

1. НОЛЬ БИНАРНЫХ АССЕТОВ. Ландшафт, спрайты, звук, музыка, интерфейс —
   всё считается кодом в рантайме: текстуры через SetPixels32, звук
   синтезируется формулой в AudioClip, интерфейс на UI Toolkit строится
   из C#. Единственное исключение — текстовый ассет PanelSettings, без
   него собранный плеер даёт серый экран (см. ниже). Причина правила:
   проект должен целиком жить в git и читаться агентом.
2. Сцена одна и пустая. Точка входа — [RuntimeInitializeOnLoadMethod],
   весь мир поднимается кодом. Никакого перетаскивания в инспекторе.
3. Никакого автостарта матча. С первого дня есть App со стейт-машиной
   «Меню → Матч → Итоги». Вкрутить меню в игру, которая стартует сама из
   Awake, потом дороже, чем написать стейт-машину сразу.
4. Ввод — только через интерфейс IGameInput с игровой семантикой (Move,
   AimUp, FireHold, Jump), никогда не через KeyCode напрямую в геймплее.
   Реализации: клавиатура, тач, геймпад, бот. Бот — такая же реализация,
   не отдельная ветка кода.
5. Каждая фаза заканчивается тестом в Assets/Editor/*.cs с пунктом меню и
   статическим Run() для -executeMethod, и записью в PLAN.md о том, что
   закрыто. Тест печатает в консоль строку вида «PHASE3: OK».
6. Язык кода и комментариев — английский, язык документов и общения —
   русский.

Стек: Unity 6000.6, C#, Physics2D, com.unity.inputsystem, UI Toolkit.
Без сторонних пакетов и без URP — встроенный конвейер, спрайты.

Сейчас: создай скелет проекта (Packages/manifest.json, ProjectSettings,
пустую сцену, Assets/Scripts/{App,Input,Game,Terrain,Weapons,UI,AI,Audio,Util},
Assets/Editor), напиши PLAN.md с таблицей из десяти фаз (приложу отдельно),
README.md с разделами «Запуск», «Управление», «Как устроено», «Проверка»,
и останови работу. Дальше я буду говорить «Фаза N» — и жду её целиком:
код, прогон теста, обновление PLAN.md.
```

Отдельным сообщением сразу после — таблица фаз из раздела 2.

### Промт на каждую итерацию

После скелета вся работа идёт одним словом: **«Фаза 4»**. Чтобы это работало,
в память проекта (`~/.claude/projects/<slug>/memory/`) кладётся файл типа
`project` с текстом: «Фаза N — строка N из таблицы PLAN.md; выполнять целиком:
код, тест, обновление PLAN.md». Без этой записи после компактации контекста
«Фаза 6» перестаёт что-либо значить.

## 2. План: десять фаз с нуля

Порядок отличается от Wormfall принципиально. Там фазы разбирали готовый
прототип: ввод, интерфейс, меню — потому что всё это уже было прибито гвоздями.
С нуля дешевле сразу заложить абстракции и строить геймплей поверх них.

5 → 6 → 7 делает его мобильным. 8 и 9 идут параллельно после 4.
10 — последней, но её мины стоит прочитать до фазы 5.

**Оценка:** в Wormfall фаза 1 заняла отдельную сессию, фазы 2–9 — по одной
каждая, фаза 10 — полторы (собранный плеер не запускался). С нуля закладывать
столько же: одна фаза — один заход.

## 3. Мины, за которые уже заплачено

Это главное, что переносится в новый проект. Каждый пункт стоил сессии отладки.

**1. Коллайдер ландшафта режется на чанки сразу, а не потом.** Один
`PolygonCollider2D` на весь мир пересобирается при каждом взрыве: 93 мс на
кадр. Лечение — 45 чанков по 128 пикселей на дочерних объектах, взрыв трогает
два-три: 1,7 мс. Текстура тоже обновляется прямоугольником изменённого, а не
полным `SetPixels32`. Заложить в фазу 1 — переделывать позже дороже, потому что
к ландшафту к тому моменту привязаны спавн, трава и вода.

**2. `PanelSettings`, созданный через `CreateInstance`, не работает в сборке.**
ICU-данные Unity кладёт только при импорте ассета. В плеере текстовый движок UI
Toolkit падает `NullReferenceException` в `UITKTextHandle.ShapeText` — **серый
экран при работающем звуке**. В редакторе баг не виден никогда: ни в PlayMode,
ни в тестах. Нужен текстовый ассет `Resources/UiPanel.asset` +
`UnityDefaultRuntimeTheme.tss`, создаваемый редакторным скриптом, и загрузка
через `Resources.Load` + `Instantiate`. Единственное исключение из правила
«ноль ассетов».

**3. Модель полёта в боте обязана шагать тем же интегратором, что и движок.**
Точное интегрирование (`p += v·dt + a·dt²/2`) расходится с реальным снарядом на
1,5 юнита. Unity считает полуявным Эйлером с шагом `Time.fixedDeltaTime`:
сначала силы к скорости, потом скорость к позиции. Ветер — ускорение, а не сила.

**4. Условная компиляция — про доступность типа, рантайм-проверка — вторая
линия.** `Handheld.Vibrate()` под `if (Application.isMobilePlatform)` валит
сборку Standalone с `CS0103`: типа `Handheld` там нет вовсе. Нужен
`#if UNITY_ANDROID || UNITY_IOS`.

**5. `overrideDefaultApplicationIdentifier`.** Без флага Unity молча держит
`com.DefaultCompany.*` и игнорирует заданный bundle id.

**6. Проверять запуском собранного плеера, а не только тестами.** Все тесты
гоняют PlayMode в редакторе — целый класс багов (пункт 2) они не ловят
принципиально. Диагноз брать из `Player.log`, а не из лога сборки.

**7. Windows IL2CPP кросс-компиляцией с macOS не собирается вовсе.** Цель в
`BuildAll` держать, артефакт делать на Windows-хосте.

## 4. Инфраструктура вокруг агента

Не про игру, но без этого план не выполняется.

**MCP-мост к живому редактору.** `com.unity.pipeline` в манифесте + сервер
`unity mcp` в `.mcp.json` — 143 инструмента, включая `console`, `run_tests`,
`eval`, `screenshot`, `editor_play`. Альтернатива (`-batchmode -executeMethod`)
требует закрытого редактора: каждый прогон теста — перезапуск. Ставить в фазе 1.
`.mcp.json` подхватывается только при старте сессии.

**Батчмод не запускается, пока проект открыт в редакторе** (лок на папке).
Обход: скопировать `Assets`, `ProjectSettings`, `Packages` в скретчпад (~600 КБ,
бинарных ассетов же нет) и гонять тесты там.

**Консоль редактора держит 2000 записей** и забивается спамом. Надёжнее
`grep -a "PHASE" Logs/Editor.log | tail`.

**`com.unity.ide.visualstudio@2.0.28` роняет редактор** ассертом Mono при каждой
перезагрузке доменов. Закрепить `2.0.22`.

**Быстрая проверка компиляции без Unity:** `dotnet build Game.sln`.

**План живёт в двух местах** — `PLAN.md` и артефакт-дорожная карта — и правится
только вместе, в одном заходе.
